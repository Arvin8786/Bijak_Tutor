# BijakLearn Junior — operational launch checklist

This repository is a **functional learning pilot**. Do not claim it is a complete, officially teacher-approved Malaysian KSSR curriculum or a fully secured production enrolment platform.

## 1. GitHub Pages demonstration
GitHub Pages publishes the static React PWA. It supports browsing draft lessons and preschool activities without a real login. On the home page, **Remember demo progress** stores fictional nickname profiles and scoring evidence in the browser for roughly 30 days, with a Clear demo progress control. This is optional, local, unencrypted device storage. Do not enter a child's real name or private records.

## 2. Separately hosted Apps Script parent-account pilot
Use the **release/** directory generated by GitHub Actions `npm run build`:
- `App.html`
- `Code.gs`
- `CurriculumImport.gs`
- `CurriculumData.gs`
- `AdminOperations.gs`
- `AccountAccess.gs`
- `AnswerMarking.gs` (generated from the shared marking rules)
- `appsscript.json`

1. Create a **private** Google spreadsheet using a dedicated operator Google account; never set it to “Anyone with link can edit.”
2. Create an Apps Script project owned by that account. Copy the generated files, preserving their names, and configure the Apps Script manifest.
3. In **Script Properties**, set:
   - `SPREADSHEET_ID`: the private spreadsheet ID
   - `GOOGLE_CLIENT_ID`: the OAuth client ID for Google Identity Services
   - `PIN_PEPPER`: a randomly generated long secret; do not commit it
   - `ACCOUNT_ADMIN_GOOGLE_SUB`: the verified Google account ID of the operator who can manage access. Use the exact `sub`, not an email address. Keep this setting private.
4. From the Apps Script editor **run** `initializeDatabase_` and `importFullJuniorCurriculum_`. Review the returned import counts. These functions are deliberately private to client-side `google.script.run` calls.
5. In Google Cloud Console, configure an OAuth consent screen and authorised domains/origins appropriate to the deployed Apps Script HTML Service. Verify the client ID and deployment identity; an ID token must be checked server-side.
6. Deploy as web app **Execute as: Me** with only the access needed for your permitted pilot. The script verifies each parent's Google ID token and authorises linked child records.
7. Test with *fictional* accounts first: registration, child ownership, lessons, server-checked quiz answers, parent PIN, review report, expired plan and family separation.

**Important:** The GitHub Pages app is a separate static deployment. It does not authenticate to private Apps Script just because the Apps Script project exists. Users wanting real parent accounts must use the separately deployed Apps Script HTML-service URL until a properly authenticated cross-origin backend is developed and security-reviewed.

## 3. Account activation and blocking

Run `initializeDatabase_` before updating the web app. It creates the private `AccountAccess` sheet without modifying existing parent or student records. The administrator signs in to the Apps Script web app and opens **Manage account access**. If the operator has never signed in and their Google ID is unknown, sign in on the test deployment and find that request in the private sheet. Verify the operator's identity and copy the text after `google:` from its `accountKey` into `ACCOUNT_ADMIN_GOOGLE_SUB`. Sign in again to open the controls.

- Existing parent accounts retain their access. A new Google account needs approval before it can create a parent profile or use protected features.
- **Block** requires a reason. The next protected request is denied even if the user still has an otherwise valid sign-in token. An operation already authorized may finish. **Restore access** reactivates the same account and its existing records.
- The private sheet records requests, decisions, timestamps, and the administrator's Google account ID. Only the configured operator can manage access through the web app. Change the administrator through Script Properties.
- Validate with two test accounts. Verify the second account starts pending, gains access after approval, and is denied on its next protected request after blocking. Verify it cannot manage other accounts and that restoration preserves its data.
- Update the intended deployment and archive any reachable older deployment that uses the same database. Old versions lack the new access check.

### Owner-only membership administration
In the Apps Script editor, use these private operations only after independent, documented approval:
- `approveScholarship_(applicationId, 12)`: sets verified Premium Kasih status with expiry
- `declineScholarship_(applicationId, "reason")`: records rejection
- `verifyManualPayment_(parentGoogleSub, bankReference, amountRM, months)`: records a bank-confirmed payment and creates Premium access
- `revokeMembership_(parentGoogleSub, "reason")`: revokes active subscriptions
These cannot be called by the student UI, and **must not** be published as unrestricted web methods. Store neither identity documents nor income evidence in the public application.

After upgrading, run `initializeDatabase_` to append the optional `answerFormat` question column. Existing rows retain strict text marking unless an educator explicitly assigns `equivalent-number` to a numeric equivalence exercise. The additive importer preserves existing reviewed questions; it does not overwrite them with changed drafts.

## 4. Content validation gate
The `release/CURRICULUM_COVERAGE.json` file is a transparent list of curriculum catalogue combinations with counts of draft lessons, exercises, and approved materials. It explicitly does not calculate a percent of complete national syllabus standards because validated DSKP standard mappings have not been built for every stream/year.

Before a course can be called complete:
- Check applicable KPM/DSKP and alignment documents for the exact year and school stream.
- Independently review all standards, examples, answers and language.
- Mark content `TEACHER_APPROVED` only with reviewer credentials and a traceable source/version.
- Run independent assessment-quality tests with students and qualified educators.
- Validate privacy, consent, data retention, recovery, cross-family access and production traffic.

## 5. Limitations to close before public subscriptions
- A secure static-PWA-to-backend identity and authorisation bridge.
- Teacher-approved full KSSR coverage, including optional languages and school-stream variations.
- Authenticated parent/session management, account recovery, consent and deletion workflows.
- Verified anti-replay server-issued assessment sessions rather than trusting self-reported hints.
- Real payment reconciliation, scholarship-document privacy and administrative audit review.
- Tested capacity, backups, rollback and incident response.
